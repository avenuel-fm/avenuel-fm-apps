[1. 온도가 옛 프로그램보다 낮게 나오는 문제 — 가장 중요]
증상: samples\s3.jpg 의 스팟 3점이 정답 28.9 / 28.9 / 28.8 인데 브라우저는 28.3 / 28.3 / 28.2 로 0.6도 낮다. s1·s2 는 같다.
원인(코드에서 확인): flir_parser.js 의 FlirCalculator.getTempAt 이 Planck 값(R1, B, F, O, R2)만으로 계산한다. 방사율은 읽어 놓고 쓰지 않으며, 반사 온도·대기 온도·상대 습도·물체까지 거리·대기 투과율은 아예 안 읽는다. FLIR 프로그램은 이것들을 모두 적용한다.
할 일:
 a. 사진 안 카메라 정보(FFF 태그 32 CameraInfo)에서 다음을 읽는다: 방사율, 반사 겉보기 온도, 대기 온도, 상대 습도, 물체 거리, 외부 광학 온도·투과율, 대기 투과율 상수(ATA1·ATA2·ATB1·ATB2·ATX). 위치는 FLIR 카메라 정보 구조(ExifTool 의 FLIR 문서, 「Thermal Image」 계산식)를 따른다.
 b. FLIR 표준 계산식으로 원시 신호 → 물체 온도를 계산한다: 대기 투과율(거리·습도) → 반사·대기 성분 빼기 → 방사율 보정 → Planck 역변환. getTempAt 한 곳만 고치면 모든 화면(스팟 온도·표·ΔT)에 반영되게 한다.
 c. 화면에서 방사율·반사온도·거리를 사진 값 그대로 쓰되, 보고서 화면에 「적용값: 방사율 0.95 · 반사 20℃ · 거리 1m」처럼 작게 보여 준다(사용자가 FLIR 와 비교하기 쉽게).
 d. 시험: samples\s1~s3 전부, 스팟 위치가 읽히는 모든 사진에서 옛 값과 소수 첫째 자리까지 같아야 한다(오차 0.1℃ 이내). 안 되면 어느 값 때문인지 원인을 적어 알려 준다. 맞춘 값을 억지로 더하거나 빼는 보정(0.6 더하기 같은 것)은 금지.

[2. 스팟 위치 학습이 스팟을 못 읽는 문제]
증상: 학습용으로 사진 9장을 넣으면 「학습 완료: 9장 중 스팟이 포함된 0장의 위치 데이터를 누적 학습했습니다.」 라고 나온다.
원인 후보(코드에서 확인): flir_parser.js findSpot 이 UTF-16 글자 「Sp1」「Sp2」「Sp3」 바이트(53 00 70 00 31 00 …) 앞 4바이트를 좌표로 읽는 한 가지 모양만 안다. samples\s4~s8 은 옛 프로그램(FlirTool)이 스팟 3점이 있다고 읽는데 그런 글자 바이트가 사진 안에 없다(스팟이 다른 모양으로 저장됨). s3 에는 UTF-16 「Sp#」 6개와 일반 글자 「Sp#」 3개가 같이 있다. 즉 사진마다 스팟이 저장된 모양이 여러 가지일 수 있다.
할 일:
 a. samples 의 사진들에서 FFF 태그 목록과 측정(스팟) 기록이 어디에 어떤 모양으로 있는지 조사해서, 옛 값(sN.flirtool.json 의 sp1·sp2·sp3 x,y)과 맞는 읽는 법을 모두 구현한다. 사진 8장 모두 옛 값과 같은 위치가 나와야 한다.
 b. 스팟이 정말 없는 사진이면 「학습 완료」 대신 「이 사진에는 스팟 위치 기록이 없어 학습하지 못했습니다」 라고 사진별로 알려 준다. 0장이면 성공처럼 보이지 않게 한다(경고 색 글자는 규칙상 오류 문구만 빨강).
 c. 학습 자료로 .jpg 말고 FLIR Thermal Studio 보고서(.atr)도 받는다. 사용자가 처음부터 「기존에 만든 리포트를 학습」시키려 했고, .atr 은 zip 이다(JSZip). 안의 cactus/*.bin 중 _MT.bin 이 아닌 사진 파일들을 같은 파서로 읽어 스팟 위치를 학습한다. 옛 PC 판은 이렇게 했다(engine/spot_learner.py 참고).
 d. 사진을 옮기며 스팟 위치를 다시 써 넣는 patchSpots 도 같은 점검: 기록 자리를 못 찾으면 조용히 실패하지 말고 화면에 알린다. 새로 만든 .atr 을 FLIR Thermal Studio 에서 열었을 때 스팟이 옮긴 자리에 보이는지 사용자가 확인할 수 있게, 「스팟 기록을 새로 써 넣었는지」 여부를 보고서 만들 때 알려 준다.

[3. 버튼: PDF 저장 · 내려받기]
화면 위쪽 버튼 줄을 이렇게 바꾼다 (현재 「인쇄 / PDF 미리보기」「리포트(.atr) 생성 및 다운로드」).
 · 「PDF 저장」(처음) — 누르면 보고서 쪽들을 PDF 한 파일로 만들어 서버에 올리고 구글 드라이브로 백업한 뒤, 저장되면 이 버튼이 「PDF 보기」로 바뀐다(누르면 새 탭에서 PDF 를 연다).
 · 「내려받기」 — 지금의 .atr 만들기·내려받기 기능 이름만 바꾼다.
 · 쪽을 고치거나(사진·위치·스팟·측정자·날짜·제목 변경) 새 문서가 되면 「PDF 보기」는 다시 「PDF 저장」으로 돌아간다(옛 PDF 가 새 내용과 다르므로).
 · 남색으로 칠한 주요 버튼은 화면에 하나만 (결정 150). 「PDF 저장」을 남색 채움으로, 「내려받기」는 흰 바탕 남색 테두리로.
PDF 만들기:
 · 라이브러리는 업무지원이 쓰는 것과 같은 고정 판: https://cdnjs.cloudflare.com/ajax/libs/html2pdf.js/0.10.1/html2pdf.bundle.min.js
 · 지금 「인쇄 / PDF 미리보기」 화면(btnPrint)을 PDF 로 만들어도 된다. 이 버튼은 없앤다(PDF 저장·PDF 보기가 대신함).
 · 파일 이름: 「점검일자_열화상점검-제목.pdf」 (예: 2026-11-20_열화상점검-2026년 4분기 EPS 1층.pdf).
저장 순서(통로 WS_THERMAL 사용, 모두 Promise):
 1. blob = html2pdf 결과
 2. up = await bridge.upload(blob, '이름.pdf')            → { path, url }  (서버 저장, 원본 그대로)
 3. dr = await bridge.toDrive(up.path, '이름.pdf')        → { ok, url }    (구글 드라이브 백업, 업무지원이 처리함 — 작성기는 부르기만)
 4. await bridge.saveReport({ title, inspector, date, path: (.atr 경로가 없으면 빈 값), pdf_path: up.path, pdf_url: up.url, drive_url: dr.url, pages, max_dt })
 5. 성공하면 버튼을 「PDF 보기」로(눌렀을 때 열 주소: drive_url 이 있으면 그것, 없으면 up.url).
 · toDrive 가 오류를 던지면(드라이브 쪽 문제) 서버 저장은 이미 됐으니 「서버에는 저장했지만 구글 드라이브 백업은 못 했습니다: (이유)」 알림을 띄우고 버튼은 「PDF 보기」로 바꾼다(주소는 up.url).
 · 통로가 없는 단독 실행(mock_bridge.js)에서는 PDF 를 내려받기만 하고, 「드라이브 백업은 업무지원 안에서만 됩니다」 안내. mock_bridge.js 의 toDrive 는 이 규격대로 { ok, url } 을 흉내 낸다.
 · 이미 saveReport 가 .atr 내려받을 때도 불린다. 같은 보고서(제목·날짜 같음)에서 두 번 기록되어도 괜찮게 하되, 한 번의 PDF 저장 = 기록 한 줄이 되게 한다.
통로 추가 (업무지원 쪽은 Claude Code 가 만든다. 작성기는 규격대로만 부른다):
 · toDrive(path, name) → { ok:true, url } 또는 오류 던짐
 · saveReport 의 입력에 pdf_path, pdf_url, drive_url 세 칸이 더해진다(없어도 되는 칸).

[4. 뒤로 버튼]
작성기 안에는 뒤로 버튼이 없다. 업무지원 화면 쪽이 뒤로를 두 개 그리고 있어서(작은 것 + 긴 것) Claude 가 업무지원 쪽에서 긴 것 하나만 남긴다. 작성기는 할 일 없음. 다만 업무지원 아래 긴 뒤로 줄이 화면 맨 아래에 붙으므로, 작성기 화면 높이는 부모 창 높이에 맞춰(100% 고정, 자기 안에서 스크롤) 아래 버튼이 가려지지 않게 한다. 작성기 화면 맨 아래 쪽에 고정 줄을 새로 만들지 않는다.
