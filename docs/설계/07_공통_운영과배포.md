## 14. 배포 · 짧은 주소 (v1.3에서 다시 씀 — 결정 6 변경, WS-15)
- 수정은 항상 **배포 관리 → 기존 배포 ✏ → 새 버전**으로 올립니다. 그래야 `/exec` 주소가 유지됩니다. "새 배포"는 하지 않습니다.

### 14.1 주소 체계 (필수 공통 요소)
```
직원에게 알려 주는 주소        QR 라벨·메일 속 링크
tinyurl.com/avenuel-ws          https://계정.github.io/fm/ws/?fe=…
        │ (TinyURL)                      │
        ▼                                ▼
 바로가기 페이지(껍데기) — GitHub Pages `fm/` · 웹앱을 전체 화면 iframe으로 띄움
        │  apps.js 의 exec 주소 · ?뒤 값은 그대로 넘김
        ▼
 구글 웹앱 …/macros/s/…/exec   (doGet 출력에 ALLOWALL)
```
- **왜 껍데기를 거치나**: 브라우저에 구글 계정이 2개 이상 로그인되어 있으면 `/exec`가 `/u/1/` 주소로 바뀌면서 「Drive · 현재 파일을 열 수 없습니다」가 납니다. 다른 페이지 안(iframe)에서 열면 생기지 않습니다. TinyURL은 주소를 넘겨주기만 하므로 `/exec`에 바로 연결하면 같은 오류가 납니다.
- **각 앱이 할 일 (모든 앱 필수)**
  1. `doGet`의 모든 HTML 출력에 `.setXFrameOptionsMode(HtmlService.XFrameOptionsMode.ALLOWALL)`
  2. 앱 `설정` 탭 `바로가기주소`(예: `https://계정.github.io/fm/ws/`). 값이 있으면 QR·메일·링크 주소를 이것으로 만들고(`publicUrl_()`), 없으면 `/exec`
  3. 껍데기 `fm/apps.js`에 앱 코드별 `exec` 주소를 적음. `fm/{hub,ws,dw}/` 폴더가 앱마다 하나
- **TinyURL**: 지정 이름으로 만들고 Long URL에는 **껍데기 주소**를 넣습니다. 예: `tinyurl.com/avenuel-fm`(HUB), `tinyurl.com/avenuel-dr`(DW), `tinyurl.com/avenuel-ws`. 이름은 만들 때 확정합니다.
  - 무료 TinyURL은 목적지를 바꿀 수 없습니다. 웹앱 주소가 바뀌어도 `apps.js` 한 줄만 고치면 TinyURL·QR은 그대로입니다.
- **QR에는 TinyURL을 쓰지 않고 껍데기 주소를 바로 넣습니다.** QR마다 붙는 값(`?fe=` 등)이 TinyURL을 거치면 빠질 수 있기 때문입니다.
- 껍데기가 12초 안에 웹앱을 띄우지 못하면 「새 창에서 열기」 버튼을 보여 줍니다.
- 껍데기 안의 구글 웹앱 화면에서는 실시간 카메라가 막힙니다(구글 격리 칸). 앱 안 사진은 기본 카메라 앱으로 받습니다 (03 9.5).
- **껍데기가 직접 띄우는 화면 (결정 42·44)**: 실시간 카메라가 필요한 화면은 `fm/{앱}/` 아래 HTML로 두고, 그 주소로 들어오면 껍데기가 웹앱을 띄우지 않고 그 화면을 엽니다. 예: `fm/ws/?fe=…` → `fm/ws/check.html?fe=…`.
  - 그 화면은 웹앱의 `GET ?api=…` / `POST`(본문 `text/plain` JSON)로만 데이터를 주고받습니다. 쿠키를 쓰지 않아 여러 계정 오류가 없습니다.
  - 화면 파일은 앱 코드(`src/`)에서 만들어 내고, 바꾸면 GitHub `fm/`에도 다시 올립니다. 설치 안내에 「GitHub에 올릴 파일」을 적습니다.
- 직원 휴대폰 홈 화면에는 **HUB 짧은 주소 1개**를 기본으로 둡니다. 자주 쓰는 앱은 그 앱 짧은 주소를 더 둘 수 있습니다.
- 짧은 주소는 공통 DB `앱목록.short_url`과 같게, 껍데기 주소는 `앱목록.pc_url` 옆 메모로 관리합니다.

## 16. 새 앱 추가 절차 (앞으로의 기준)

### 16.1 메뉴로 넣을지, 새 앱으로 만들지
- **기본은 WS 메뉴로 넣는 것**입니다. 앱이 늘면 앱 사이 이동마다 2~3초가 걸리고, 관리할 배포도 늘기 때문입니다.
- 아래 중 **하나라도 해당하면** 새 앱으로 만듭니다.
  1. 쓰는 사람이 다릅니다. 예: 외부 업체나 다른 팀이 주로 씀
  2. 데이터가 WS DB를 크게 키웁니다. 예: 한 해 수만 줄의 계측 기록
  3. 배포 주기나 보안 수준이 다릅니다
  4. WS 화면 코드가 너무 커집니다. 기준: 화면 파일 하나에 약 300KB 이상

### 16.2 새 앱 만들기 체크리스트
1. 앱 코드(영문 2~3자)와 폴더 번호(`30`, `40` …)를 정하고, `01_공통_구조와데이터.md`의 2.1과 4장 등록부에 적습니다.
2. **기능 문서 하나를 새로 만듭니다** (`{앱코드}_{기능}.md`, 00 목차의 「새 기능 문서 틀」). 공통 규칙은 다시 쓰지 않고 장 번호로 가리키기만 합니다.
3. **공통 틀**을 복사합니다: `common.css`, 로그인·입장표, `cdb`, 사진, 검색키, PDF 대기, 위 막대.
   - 공통 틀 파일은 고치지 않습니다. 바꿔야 하면 17장 절차를 따릅니다.
4. 앱 DB에 필수 탭(`설정`, `변경기록`, `색인대기`)을 만듭니다.
5. 문서를 만들 때는 반드시 `문서색인`에 기록합니다. 사진은 `사진색인`에 기록하고, 이름 규칙(5장)을 지킵니다.
6. `?api=ping`과 `?api=summary`를 만듭니다. `todos`에는 역할을 넣습니다.
7. 권한표(7.4)에 줄을 추가합니다.
8. 시험을 통과해야 합니다.
   - 서버 시험
   - **다른 앱과 동시에 색인 쓰기**
   - 13가지 화면 크기 (아이패드 엔진 시험은 하지 않음, 결정 31)
   - 입장표 왕복 (HUB ↔ 새 앱 ↔ WS)
9. 배포(14장) 후 HUB에 앱을 등록하고, 껍데기 `apps.js`에 주소를 넣고, TinyURL을 만들고, 설치 안내를 씁니다.

### 17.2 버전 규칙
- **공통 규격 버전** `v1.x`: `00_목차_읽는법.md`에 적힌 버전입니다. 공통 문서(01~07) 중 하나라도 규칙이 바뀌면 올립니다.
  - 열 추가, 코드 추가처럼 **기존 앱이 그대로 동작하는 변경**은 `v1.1 → v1.2`로 올립니다.
  - 기존 앱이 깨지는 변경은 `v2.0`으로 올리며, 모든 앱을 같은 날 배포해야 합니다.
- **공통 틀 버전**: 공통 틀 파일 맨 위에 `COMMON_VERSION`을 적습니다.
  - ping으로 알리고, `앱목록.공통틀버전`에 기록합니다.
  - HUB는 앱끼리 버전이 다르면 노란색으로 표시합니다.
- **변경 순서**
  1. 바꾼 공통 문서의 판과 00 목차의 공통 규격 버전을 올리고, `90_결정과이력.md` 부록 B에 적습니다.
  2. 영향받는 기능 문서와 설치 안내에 반영합니다.
  3. 공통 DB 열 추가는 HUB가 먼저 합니다.
  4. 앱 배포는 DW → WS → 새 앱 순서로 합니다.
  5. `정보.스키마버전`과 `앱목록.버전`을 갱신합니다.
- **공통 틀은 라이브러리로 공유하지 않고 복사해서 씁니다.**
  - GAS 라이브러리는 불러오기가 느리고, 라이브러리가 바뀌면 모든 앱이 동시에 영향을 받기 때문입니다.
  - 대신 버전 표시(위)로 서로 어긋난 것을 찾아냅니다.
