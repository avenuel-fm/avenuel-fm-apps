## 1. 읽는 법 (토큰·속도 절약 규칙)
1. **어떤 작업이든 이 목차를 먼저** 읽습니다. 아래 「핵심 규칙 요약」으로 대부분 판단합니다.
2. 그다음 **작업하는 기능 문서 하나만** 읽습니다. 예: 소화기 라벨을 고치면 `WS_소화기점검.md`.
3. 기능 문서가 가리키는 공통 장(예: 「9.3」)이 **이번 작업에 직접 걸릴 때만** 그 공통 문서를 엽니다.
4. 결정이 이미 있는지 헷갈릴 때만 `90_결정과이력.md`를 엽니다.
5. 각 문서 맨 위 「요약」으로 먼저 판단하고, 필요한 장만 찾아 읽습니다.

## 3. 진행 원칙 (필수)
1. 사용자가 **"진행시켜"** 라고 하기 전에는 코딩하지 않습니다. 설계 변경, 기능 추가, 수정 모두 먼저 확인을 받습니다. 단 「이번 묶음은 확인 없이 진행·배포까지」라고 미리 말하면 그 묶음은 끝까지 진행합니다 (결정 78).
2. (뺌, 결정 37 — 개선안 두 개 이상 규칙 없앰)
3. 코드를 바꾸면 문서도 맞추되, **묶음 끝에 한 번에** 정리합니다 (결정 78, 전: 결정 37). 수정 요청은 `docs/수정요청_대기목록.md`에 모읍니다.
4. 화면은 **시안(이미지)을 먼저** 보여 드립니다. 글자·아이콘·색·간격 같은 작은 수정은 시안 없이 결과 화면만 (결정 78). 시험은 작업 중엔 고친 부분만, 묶음 끝에 전체.
5. **필수 공통 요소**(17.1)를 바꿀 때는 모든 앱을 함께 고칩니다.
6. 문서를 고치다 새 충돌을 찾으면 임의로 정하지 않고 사용자 확인을 받습니다.
7. **새 기능이 생기면 그 기능 문서 하나만 새로 만듭니다** (아래 5장 틀). 다른 기능 문서나 공통 문서에 그 기능 내용을 쓰지 않습니다. 공통 규칙이 바뀌어야 할 때만 해당 공통 문서를 고칩니다.
8. **고친 문서만** 판을 올리고, `90_결정과이력.md` 부록 B에 한 줄 적습니다. 공통 문서(01~07)의 규칙이 바뀌면 이 목차의 공통 규격 버전도 올립니다.
9. **다른 대화방(도면협의)과 맞추기**: 그 방에는 바뀐 문서 파일만 넣습니다. 받은 쪽은 문서 맨 위 판을 보고, 더 새 판이면 바꾸고, 같은 판인데 내용이 다르면 사용자에게 확인합니다.
10. **결정 번호 나누기** (결정 38): 35번부터 **업무지원 방은 짝수(36, 38, 40…), 도면협의 방은 홀수(35, 37, 39…)**만 씁니다. 같은 날 두 방이 결정을 만들어도 번호가 겹치지 않습니다.
11. **보낼 파일 빠짐없이**: 문서를 고친 방은 부록 B 그 줄에 적은 파일을 **모두** 묶어 다른 방에 보냅니다. 받는 방은 부록 B에 적힌 파일이 다 왔는지 먼저 확인하고, 빠진 것이 있으면 사용자에게 알립니다.

## 4. 핵심 규칙 요약 (대부분 여기서 판단)
1. **앱 = Apps Script 웹앱 + 전용 시트.** 실행은 시설팀 공용 계정, 접근은 모든 사용자. 자료는 드라이브 `시설팀 통합업무/`.
2. **데이터 주인은 하나**: 직원·파트·공지·검색사전·주소록 = HUB, 매장·문서번호 = DW, 각 앱 업무 기록 = 그 앱. 다른 앱 DB는 읽기만, 알릴 일은 공통 DB 색인에 (3장).
3. **공유 탭**: 덧붙이기만, 자기 줄만 고치기, 지우지 않고 `삭제여부=Y`, 열 이름으로 읽기 (W1~W6). **모든 시트 값은 앞에 `'`를 붙여 글자로 쓰고, 읽을 때 날짜로 바뀐 칸은 되돌림** (결정 54).
4. **ID** `{앱}-{종류}-{YYYYMMDD}-{###}`, 사진 `PH-{앱}-{YYYYMMDD}-{####}`. 종류 코드: WS `WL PF DF TB IN SC FE FC`, DW `RV` (4장).
5. **이름** `YYYY-MM-DD_작업명_###.jpg`, 띄어쓰기·특수문자 → `-`, 같은 날 같은 이름 `(2)` (5.1).
6. **로그인**: 개인 PIN(휴대폰 뒷 4자리), 직원 변경 불가, 5회 틀리면 5분 잠금(기기와 상관없이 많이 틀리면 10분 전체 잠금, 결정 74·39), 기기 표는 다음 오전 6시(근무일 시작)까지(결정 60), **근무일 첫 로그인은 PIN + 서명, 서명 안 하면 로그인 안 됨**(결정 56·60), 앱 이동은 입장표 `?t=` (7장). **DW만 예외**: 소장·부소장 PIN 2개 방식 그대로 (결정 36).
7. **권한**: 서버가 확인. DW는 소장·부소장 전용 단독 앱, 다른 사람에게 HUB의 DW 카드는 회색 비활성 (결정 32). 하자 발송 = 소장·부소장·파트장 (7.4).
8. **사진**: 기기에서 1600px·70%로 줄여 5장씩(문서 사진은 2400px·85%), 썸네일 320px. **모든 사진 칸은 가로 4:3, 자르지 않고 줄여 넣기, 남는 곳 연회색**, 누르면 원본 확대 (9장). 카메라는 앱 안에서는 기본 카메라 앱, 안내선이 필요한 화면만 바로가기 페이지에서 실시간 (9.5).
9. **PDF**: 먼저 제출 완료, PDF는 이어서. 10분마다 재시도, 3번 실패하면 오류기록 (11.2). 결재는 결재자 직인, PIN 다시 묻지 않음.
10. **디자인**: 도면협의 `Styles.html` 변수 이름·값, 입력칸 16px, 버튼 44px (12장). 배포 전 화면 검사는 13가지 크기만, **아이패드 엔진(WebKit) 시험은 하지 않음** (결정 31).
11. **주소**: 직원용 TinyURL → 껍데기(GitHub Pages `fm/`) → `/exec`. QR·링크는 껍데기 주소 직접. 모든 앱 `ALLOWALL` + `설정.바로가기주소`. 배포는 항상 「새 버전」 (14장).
12. **한도**: 메일 하루 100명(80명부터 경고), 예약 작업 하루 90분, 동시 실행 30 (13.2).
13. **앱 간 API**: `?api=ping`, `?api=summary`(`LINK_KEY`, 결정 80)만 (8.3).

## 5. 새 기능 문서 틀 (복사해서 씀)
- 파일 이름: `docs/설계/{앱코드}_{기능이름}.md` (예: `WS_TBM.md`, `WS_일정.md`, `WS_준공점검.md`)
- 장 번호: 그 앱의 다음 번호 (WS는 15.3.18부터)
- 만들 때: 종류 코드가 생기면 `01_공통_구조와데이터.md` 4장 등록부에도 한 줄 추가, 이 목차 2장 지도에 한 줄 추가, `WS_00_업무지원_공통.md` 범위 표에 한 줄 추가

```
# {앱} · {기능 이름}

- 판: v0.1 설계 · 수정 YYYY-MM-DD · 공통 규격 v1.x
- 담은 장: 15.x.x
- 이럴 때 읽기: …
- 목차·읽는 법: `docs/설계/00_목차_읽는법.md`

> 요약
> - (3~5줄: 무엇을, 누가, 핵심 규칙, 남은 것)

---
#### 15.x.x {기능 이름}
1. 화면 흐름
2. 입력 항목 (필드 · 필수 · 제한)
3. 저장 (드라이브 폴더 · 파일 이름 · ID)  ← 공통 규칙은 장 번호로만 가리킴
4. DB 탭 (열)
5. 서버 함수 (함수 · 권한 · 하는 일)
6. 상태 · 색 · HUB 할 일(summary)
7. 남은 것 · 대기목록 번호
```
