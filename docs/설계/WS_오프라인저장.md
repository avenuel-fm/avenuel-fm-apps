# WS · 오프라인 임시 저장 (신호 끊김 대비)

- 판: **v0.2 (1차 구현·시험 완료, 배포 전)** · 작성 2026-11-21 · 공통 규격 v1.21
- **범위 확정 (사용자 11-21)**: 1차 = 소화기 QR 점검 + 공조기·온습도 입력, 소화전·공기호흡기는 그 세션 완료 뒤 같은 부품으로. 질문 2~6은 문서의 권장안대로 진행 예정(사용자가 다르게 말하면 바꿈)
- 결정 번호: **222(안)** — 90 결정표에는 아직 안 적음(다른 세션이 쓰는 중이라 합칠 때 번호 조정). 사용자가 「진행시켜」 하기 전에는 코드를 고치지 않음
- **이럴 때 읽기**: 지하·기계실에서 점검 입력이 사라지는 문제, 「저장 대기」 표시, 자동 재전송, 중복 방지를 다룰 때
- 이미 있는 공통 규칙: `03_공통_사진과파일.md` 9.1(끊김 대비)·9.4(기기 + 서버 임시 저장)에 「기기(IndexedDB)에 보관」이라고 **적혀만 있고 실제 코드는 없음**. 이 문서가 그 실행 설계

> **요약**
> - **문제**: 지금은 [전송]을 누른 순간 신호가 약하면 「보내지 못했습니다」 알림만 뜨고, 앱을 닫거나 새로고침하면 입력(사진·손글씨 포함)이 사라짐. 기기에 남기는 곳이 한 군데도 없음.
> - **해법**: 보내기 전에 **먼저 기기 안(IndexedDB)에 보관 → 신호가 되면 자동 전송 → 성공하면 보관분 삭제**. 화면에는 「저장 대기 n건」을 보여 줌.
> - **1차 범위(권장)**: ① 소화기 QR 점검 입력(사진 포함) ② 공조기 환기온도·가동시간·온습도 입력(숫자만). **소화전·공기호흡기**는 같은 부품을 그대로 끼움. 공사장 점검(사진 많음)은 2차, TBM·작업일지(서명·PDF·긴 입력)는 3차.
> - **중복 방지**: 입력마다 기기가 만든 고유 번호(`client_id`)를 붙여 서버가 같은 번호는 한 번만 받음. 입력 시각도 같이 보내 「30일 지하에서 입력 → 1일에 전송」해도 **입력한 달**로 기록.
> - **한계**: 기기를 바꾸거나 브라우저 데이터를 지우면 대기분도 사라짐. 앱이 꺼져 있으면 전송도 멈춤(아이폰은 백그라운드 전송 불가) → 다시 열 때 자동 전송.

## 3. 설계

### 3.1 기기 안 보관 — 「보낼 일 상자(outbox)」
- 저장소: **IndexedDB** `ws_outbox` 한 개. 사진·손글씨는 글자(base64)로 바꾸지 않고 **Blob 그대로** 넣음(용량 33% 절약).
- 한 건(job): `{ id(UUID = 중복 방지 번호), kind('fire_check'|'usage'|'ahu'…), staffId(직원이면), payload, files:[{key, blob, path}], entered_at(입력한 시각), workDay, state, tries, nextTry, error }`
- 용량 한도: **최대 30건 · 합계 50MB**. 넘으면 새 입력을 막고 「먼저 전송 대기분을 보내 주세요」 안내(입력이 조용히 사라지지 않게). 소화기 한 건은 약 150~250KB라 한도에 한참 못 미침.
- 브라우저가 몰래 지우지 못하게 `navigator.storage.persist()`를 요청. 아이폰 사파리는 「홈 화면에 추가한 앱」이면 7일 미사용 삭제 대상에서 빠짐 → 안내 문구에 넣음(6장).
- 토큰·PIN은 **저장하지 않음**. 전송 때 그 시점의 로그인 표를 씀.

### 3.2 끼우는 자리 (코드 수정 범위, 구현 때)
- **새 파일 `fm/ws/offline.js`** (공통 부품): 보관·재전송·대기 건수·화면 표시. 앱마다 따로 만들지 않음.
- `ws-api.js`: 위 1·2순위 함수만 「먼저 기기에 넣고 보내기」로 감쌈. 나머지 함수는 그대로.
- `app.html`: 위 막대에 「저장 대기 n건」 칩, 환경설정에 「저장 대기 목록」. `check-sb.html`: 같은 부품 불러와 전송 버튼 흐름만 바꿈.
- 서버: 새 SQL `supabase/23_offline.sql`(번호는 합칠 때 조정). 열 추가 + 함수에 받는 값 추가만, 기존 열·함수 호출은 그대로 동작(옛 화면과 호환).

### 3.3 저장 → 전송 흐름
```
[전송]/[저장] 누름
 ① 기기 보관 (먼저, 항상)  →  화면에 「이 기기에 저장했습니다」
 ② 곧바로 전송 시도 (15초 제한)
      ├ 성공 → 보관분 삭제 → 「전송했습니다」
      ├ 서버가 「안 됩니다」라고 답함(빠진 칸 등) → 대기에 넣지 않고 지금처럼 그 자리에서 안내 (보관분 삭제)
      └ 신호 문제(응답 없음·시간 초과·offline) → 「저장 대기」로 남김, 자동 재전송
```
- 신호 문제와 서버가 거절한 것을 **구분**하는 것이 핵심: 거절을 대기에 쌓으면 영원히 재전송됨.
- 사진은 **올리는 경로를 입력할 때 미리 정함**(무작위 이름을 한 번만 만듦). 올리다 끊겨도 다시 같은 경로로 올리고, 「이미 있음」은 성공으로 봄 → 쓸모없는 사진이 버킷에 쌓이지 않음(지금은 재시도마다 새 이름으로 올라가 찌꺼기가 남음).

### 3.4 자동 재전송
- 시작 시점: ① 앱·점검 화면을 열 때 ② 브라우저 `online` 알림 ③ 화면이 다시 보일 때(`visibilitychange`) ④ 대기분이 있는 동안 30초마다.
- 실패하면 30초 → 1분 → 2분 … **최대 10분 간격**(배터리·서버 보호). 한 번에 한 건씩 차례로(입력 순서대로).
- 한계: **앱을 닫으면 멈춤.** 아이폰은 백그라운드 전송(Background Sync)이 없어서, 신호 있는 곳에서 앱을 다시 열어야 자동 전송됨. 이 점을 「저장 대기」 안내에 적음. 안드로이드 크롬은 후속으로 백그라운드 전송을 더할 수 있음(1차 제외).
- 앱 파일 자체는 **서비스워커**로 기기에 복사해 둠(1차 포함, `fm/ws/sw.js`): 지하에서 앱·QR 점검 화면을 **새로 열어도** 열림. 직원 화면은 마지막으로 불러온 공조기 장비 목록 같은 「틀」도 읽기용으로 기기에 복사(없으면 입력 틀이 안 뜸).

### 3.5 중복 방지
1. **입력마다 `client_id`(UUID)** 를 기기가 만들어 서버에 보냄. 서버(소화기·공조기 등)는 같은 `client_id`가 이미 있으면 **새로 만들지 않고 그때의 결과를 그대로 돌려줌**(`fire_checks.client_id` 유일 열 추가).
2. 「서버는 저장했는데 응답만 못 받음」 상황도 같은 번호로 다시 보내면 한 건으로 끝남 → 위에서 말한 「내가 나를 덮어쓰기」가 사라짐.
3. 보내기 버튼 이중 누름은 보관 단계에서 막음(같은 입력 → 같은 `client_id`).
4. 서버가 **입력 시각(`entered_at`)** 도 받음: 입력한 달·기한 후 판정·근무일을 이 시각으로 계산(서버 시각과 어긋나도 **과거 40일 이내·미래 불가**일 때만 인정, 아니면 서버 시각).

### 3.6 충돌 처리 (다른 사람이 먼저 고친 경우)
| 입력 | 규칙 |
|---|---|
| 가동시간 (장비 한 줄) | **입력 시각이 늦은 쪽이 이김**(`updated_at` 비교). 먼저 입력했는데 늦게 도착한 값은 이미 있는 더 늦은 값을 덮지 않고 조용히 건너뜀 |
| 공조기 환기온도 (칸 단위) | **1차는 늦게 도착한 쪽이 덮음**(칸마다 시각을 따로 두지 않음 — 같은 칸을 둘이 동시에 고치는 일이 드물고, 값이 같으면 그대로). 필요해지면 칸별 시각 추가 |
| 온습도 (기록을 계속 덧붙임) | 덮을 일 없음 — 입력 번호가 같으면 한 번만, 다르면 새 기록 |
| 소화기 QR 점검 | 이번 달 입력이 이미 있고 그 `client_id`가 내 것이 아니면 **자동으로 덮어쓰지 않음**. 대기 목록에 「이미 이번 달 입력이 있습니다」 + [덮어쓰기] [버리기] |
| 작업일지·명일 작업 (`ver`) | 3차. 충돌이면 **내 입력을 지우지 않고 보관** → 「내 것 보기 / 서버 것 보기」 비교 후 선택(자동 합침 없음) |
| 서버가 점검 대상 자체를 없앰(QR 삭제 등) | 「대상이 없어졌습니다」 → [내용 보기] [버리기] |

### 3.7 로그인 표·근무일 서명(오전 6시)이 오프라인에서
- **이미 로그인된 기기**는 표가 살아 있는 동안 지하에서 입력 가능(지금도 로컬에서 표 만료만 확인).
- **로그인·근무일 첫 서명은 서버 확인이 필요** → 신호 없는 곳에서는 못 함. 「출근하며 신호 있는 곳에서 로그인 → 지하로 이동」을 안내(운영 규칙, 6장).
- **전송 때 표가 만료**(예: 지하에서 6시를 넘김)면 대기분은 그대로 두고 상태 「로그인 필요」. 다시 로그인하면 이어서 전송. **직원 입력은 입력한 직원 본인이 로그인했을 때만 전송**(다른 직원이 로그인하면 그 건은 대기 목록에 「○○ 입력 — 본인 로그인 필요」로 남고 건드리지 않음 → 작성자가 바뀌어 기록되는 일 방지). 근무일은 입력 시각 기준이라 6시를 넘겨 전송해도 입력한 근무일로 기록.
- **소화기 QR 점검**은 로그인이 없으므로 이 문제 없음(지금과 같은 권한으로 전송).

### 3.8 화면 안내 (시안 확인 대상)
- 위 막대 오른쪽 **「저장 대기 2건」 칩**(남색 테두리). 누르면 대기 목록. 0건이면 안 보임.
- 입력 화면 저장 직후: 신호 없으면 「**이 기기에 저장했습니다.** 신호가 잡히면 자동으로 보냅니다」 — **「저장되었습니다」라는 말은 서버에 들어간 뒤에만** 씀(기기에만 있는데 안심하게 만들지 않음).
- 대기 목록 줄: 이름(소화기·공조기 등) · 입력 시각 · 상태 글자(「전송 대기」「전송 중」「확인 필요」「로그인 필요」) · [지금 보내기] [버리기](버리기는 확인창).
- 전송 완료: 지금 알림 방식(토스트)으로 「대기 중이던 2건을 전송했습니다」. 실패·확인 필요만 **빨간 글자**(오류색 한 가지만, 06 문서 규칙).
- QR 점검 페이지 끝 화면: 대기면 「**아직 전송되지 않았습니다.** 신호가 잡히는 곳에서 이 화면을 다시 열면 자동으로 보내집니다. 그 전에는 이 페이지를 지우거나 사생활 보호 모드로 열지 마세요」.
- 색은 남색·회색·오류색만(공통 디자인 결정 150), 버튼 44px, 글자는 쉬운 말.

### 3.9 앱을 닫았다 다시 열면
- 보관분은 IndexedDB에 남음 → 열 때 대기 건수 칩이 바로 뜨고 자동 전송 시작.
- 입력 **중**(전송 누르기 전)에 앱이 꺼지면 지금은 사라짐. 입력 중 자동 보관(작성 중 임시 저장, 03 문서 9.4)은 **1차에서 뺌** — 소화기·공조기는 입력이 짧고 한 화면이라 효과가 작음. 작업일지 등 긴 입력(3차)에서 같이 함.

## 4. 이 기능이 도움이 안 되는 경우 (사용자 안내에 그대로 적기)
1. **기기를 바꾸거나 잃어버림** — 대기분은 그 기기 안에만 있음.
2. **브라우저 데이터 삭제 · 사생활 보호(시크릿) 모드** — 모두 사라짐. 소화기 QR을 시크릿 모드로 열면 보관이 안 되므로 감지해서 「이 모드에서는 저장 대기를 못 씁니다」 안내.
3. **아이폰에서 오래 안 열고 둠** — 사파리가 7일 넘게 안 쓴 웹사이트 자료를 지울 수 있음(홈 화면에 추가한 앱은 예외). 7일 넘은 대기분은 「오래된 대기」로 강조.
4. **앱을 닫은 채 신호 있는 곳에 감** — 아이폰은 앱을 열어야 전송됨.
5. **저장 공간 부족** — 보관이 안 되면 「저장하지 못했습니다」를 보여 주고 입력을 화면에 그대로 유지(사라지게 하지 않음).
6. **기기 등록 해제(「이 기기」)·로그아웃** — 대기분이 있으면 「전송 안 된 n건이 사라집니다」 경고 후에만 허용.
7. 로그인·서명을 지하에서 처음 하는 경우(3.7).

## 5. 시험 (구현 때)
- 서버: `client_id` 같은 번호 두 번 → 한 건, `entered_at` 달 경계(30일 입력→1일 전송 = 입력한 달), 남의 `client_id`·이미 입력 있음 → 충돌 답, 칸 단위 시각 비교. `apps/ws/test` 가짜 서버 시험에 추가.
- 화면: Playwright `context.setOffline(true)`로 ① 전송 → 대기 표시 ② 새로고침 → 대기 유지 ③ 신호 복구 → 자동 전송·건수 0 ④ 응답 가로채기로 「서버 저장 후 응답 유실」 → 중복 0건 ⑤ 표 만료 → 「로그인 필요」 ⑥ 사진 올리다 끊김 → 같은 경로 이어 올림.
- 실제 지하(B4) 시험은 사용자가 휴대폰으로 한 번 확인(비행기 모드로 대체 가능).

## 6. 운영 안내(사용자에게)
- 출근해서 **신호 좋은 곳에서 로그인·서명 → 지하로 이동**.
- 아이폰은 「홈 화면에 추가」한 앱으로 쓰면 보관분이 더 오래 남음.
- 「저장 대기」가 남았으면 신호 있는 곳(1층 등)에서 앱을 한 번 열어 둠.

## 7. 단계 (사용자 「진행시켜」 뒤)
1. 공통 부품 `offline.js` + 서비스워커 + `23_offline.sql`(소화기 `client_id`·`entered_at`) + 소화기 QR 입력 연결 + 시험
2. 공조기 환기온도·가동시간·온습도 연결(칸 단위 시각 규칙) + 대기 목록 화면
3. 소화전·공기호흡기 연결(다른 세션 완료 뒤)
4. (후속) 공사장 점검 → TBM·작업일지(작성 중 자동 보관·충돌 비교)

## 8. 사용자 확인이 필요한 질문
1. 1차 범위를 **소화기 QR + 공조기·온습도**로 할까요? 소화전·공기호흡기는 그 세션이 끝난 뒤 끼우는 것으로 괜찮은지?
2. **사진 포함**: 소화기는 사진 1장(약 45KB)이라 포함이 안전. 공사장·하자 같은 **사진 여러 장**은 2차로 미뤄도 되는지?
3. 직원 입력을 **입력한 본인이 다시 로그인해야만 전송**(작성자 오기록 방지)해도 되는지? (다른 직원이 같은 폰을 쓰면 그 사람 건은 기다림)
4. 소화기 QR 점검이 이미 있는 달에 오프라인으로 들어온 입력은 **자동 덮어쓰기 금지 + 물어보기**가 맞는지?
5. 앱을 **서비스워커로 기기에 복사**해 지하에서 새로 열어도 되게 하는 것(앱 업데이트가 한 번 늦게 반영될 수 있음)을 1차에 넣어도 되는지?
6. 「저장 대기」 알림을 휴대폰 진동·소리 없이 **화면 표시만**으로 충분한지?
